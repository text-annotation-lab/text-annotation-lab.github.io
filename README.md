# Text Annotation Lab

A teaching resource for AI-assisted text annotation and content analysis, developed for students in the Department of English at Aarhus University. Public address: <https://asca.au.dk/annotation-lab>, which embeds <https://text-annotation-lab.github.io>.

## How it works

The Lab is a static site published with GitHub Pages. Everything runs in the visitor's browser:

- Visitors enter their own API key (OpenAI, Anthropic, Gemini, or OpenRouter). Requests go directly from the browser to that provider; there is no Lab server, and keys never pass through one.
- Studies, prompts, and results are saved in the visitor's browser for this address.
- The former server routes in `app/api/*/route.ts` are now plain modules. `lib/local-api.ts` routes the interface's `/api/...` requests to them inside the browser.

## Research mode

The switch in the header turns the Lab into a tool for research. It is a view of the same study: switching either way never changes texts, prompts, or results, and the standard Lab looks and works as before apart from the switch.

- Tabs: Workspace, Runs & agreement, Export, About, and Model knowledge. The teaching pages and the guidance text written for students are not shown.
- One tab at a time: research mode works in one tab or window of a browser, so that the same requests are never sent (and paid for) twice and changes don't overwrite each other. A tab that opens in research mode while another has it shows a notice instead of the Lab (with "Open here" and the switch), and opens once the other tab is closed or leaves research mode; switching on elsewhere is refused with a note. The standard Lab takes no part. `lib/research/tab-lock.ts` holds the rule (a Web Lock), and `tests/research-tab.cjs` covers it. Research mode also asks the browser to keep the site's data when disk space runs low (`navigator.storage.persist`); the browser decides.
- API keys are entered in the header, one per provider. They are kept until the tab closes unless the visitor ticks "Remember keys in this browser," which stores them in that browser's local storage (research mode only). Keys are never part of a study, a backup, or an export.
- Runs: every annotation belongs to a numbered run that records its provider, model, reasoning effort, prompt, and answer fields (and a temperature or an output limit where one is set). "All" annotates every text, as a new run when texts already have results, and keeps the earlier results. "Remaining" annotates the texts that have no result from the current settings.
- Answer fields: each field has a type (category, ordinal scale, number, yes / no, or free text), the values it allows, and a description for the model. The allowed values are sent as part of the answer format, and an answer outside them is refused and kept for review. The shared explanation can be turned off, and "Plain text" sends no answer format at all and stores the whole reply as one column, "response." These settings are stored with the study and recorded on every run and result (`lib/answer-types.ts`, covered by `tests/answer-types.cjs`). A study that uses none of them sends exactly the requests the standard Lab sends.
- Plain-text replies that are JSON: when the whole reply is one JSON object (optionally inside a ```` ```json ```` fence), the export tables, the Excel workbook, the comparisons, and the charts have a column for each of its values next to "response," which keeps the reply as written. Nested keys are joined with an underscore, a list is kept as written, and each explanation follows its scores. A reply that holds JSON among other words is a failed result that keeps the reply, because its columns would otherwise be silently empty; prose is never judged. `lib/json-reply.ts` holds the rules and `tests/json-replies.cjs` covers them.
- Prompt caching (Processing options, off unless switched on): the prompt, which is the same for every text, is marked for the provider's prompt cache, so that later texts read it at the provider's cache rate. Anthropic gets `cache_control` on the system prompt (a five-minute entry; one hour in a batch). OpenAI caches only up to a mark inside a message, so the prompt is then sent as a developer message that carries the mark, in place of `instructions`; without the option, OpenAI caching stays switched off as in the standard Lab. Through OpenRouter, Claude and GPT models get the same marks. Gemini caches repeated prompts by itself, so there is nothing to switch. The setting is stored with the study, recorded on every result made with it, listed per run and per request in the exports, and never sent by the standard Lab. Recorded costs price cached tokens where the provider's pricing page lists a cache rate for the model (otherwise the cost stays unknown), and the estimate assumes one cache write followed by reads at its lower edge and a write for every text at its upper edge. `lib/request-settings.ts` holds the request shapes and `tests/prompt-caching.cjs` covers them.
- Any model: the Model menu lists the Lab's models, then the other models on the account behind the key (read from the provider's own list, with a refresh link), and "Other model ID…" opens a box for any ID the provider knows, such as a dated snapshot. For a model outside the Lab's lists, the request follows the model's family (for example, a fixed reasoning budget for Claude models up to 4.5, and no cache mode for OpenAI models before GPT-5.6), the reasoning settings on offer are those the provider's list names where it names them, and "model default" sends no reasoning setting at all. The Lab has no price for most such models; the cost of one is estimated once a price is typed (see "Your own price" below). A study notes that its model was chosen this way (`customModel`), and the model is then kept when the study is opened again, also in the standard Lab, whose own menu still offers only the Lab's models. Requests to the Lab's own models are unchanged. Covered by `tests/model-choice.cjs`.
- Request settings (Processing options, each off or empty unless set): a temperature, where the model takes one (Claude models that reason take none, so none is sent to them); the most output tokens a reply may use, in place of the Lab's own limit; a summary of the model's reasoning, which is kept with each result, shown in its details, and exported (`reasoning_summary`); and, for OpenAI, whether requests are kept in OpenAI's logs. A setting is sent only where it changes the request to the chosen provider and model, and a study that sets none sends exactly the requests the standard Lab sends. Temperature and the output limit are part of a run's setup; the others are recorded on each result. When a provider rejects a setting, the message names the setting. "Preview request" shows the request a run would send for the first text (the prompt as sent, the message with the text, and the settings), built by the code that sends it. `lib/request-settings.ts` and `lib/request-frame.ts` hold the rules, `lib/research/request-view.ts` the preview, and `tests/request-settings.cjs` covers them.
- Your own price (Processing options): two boxes show the Lab's price for the selected model per million input and output tokens, or "Unknown" for a model the Lab has no price for. A number typed into a box becomes your own price for that model and replaces the Lab's in the cost estimate before a run; the estimate then names the price it used. The model's other listed terms stay (the batch discount, the cache-read share, and the token multiplier), while its listed prices for long requests and for later dates no longer apply; a model without a listed price gets its provider's usual terms. Own prices are kept in this browser's local storage, per provider and model, with a link back to the Lab's price. They are not part of a study, a backup, or an export, the standard Lab does not use them, and the recorded cost of a finished run is still calculated from the Lab's listed rates. Covered by `tests/own-prices.cjs`.
- Parallel annotations: up to 128 texts at once (the standard Lab offers 1, 2, or 4, and a study set to more runs one at a time there). When a provider refuses a request for a short-term rate limit or because it is overloaded, the run waits, sends the request again, and goes on with half as many at a time, rising again as requests get through. A text is sent at most eight times. Quota, billing, and daily limits, and waits of more than two minutes, are failures like any other (see "When a text fails"). `lib/annotation-queue.ts` holds the pacing and `retryWait` in `lib/provider-errors.ts` decides what may be sent again; `tests/annotation-queue.test.mjs` and `tests/rate-limits.cjs` cover them.
- When a text fails: the text is marked "Needs attention" with the error, and the run carries on with the other texts (the standard Lab stops starting requests at the first failure, as before). When the run ends, a notice says how many requests failed, and "Remaining" sends them again (in Model knowledge, "Queue failed items for retry"). A run stops by itself only when its first requests all failed in a way every request would meet: at least three requests have come back, for at least two texts, and every one of them failed because of the connection (no HTTP reply, and not a timeout), the key, the account, or the model (HTTP 401, 402, 403, or 404, a key, billing, or quota code, or a limit that cannot be waited out), or with an HTTP 400 that is not about the size or the content of one text and that repeated with the same message. Requests under way finish and are kept. A reply that came back refused, cut off, or unreadable, a server error, a timeout, and a rate limit say nothing about the other texts and never stop a run. The mark a failed reply carries for this (`shared`) holds none of the provider's words and is never kept with a result. Batches are unaffected. `sharedFailure` in `lib/provider-errors.ts` tells the failures apart and `lib/research/early-stop.ts` holds the rule; `tests/carry-on.cjs`, `tests/research-mode.cjs`, and `tests/model-knowledge.cjs` cover them.
- Details of a text: the details under the results table have "Previous" and "Next" with the place of the text ("3 of 6"), and the J and K keys do the same while the details have the focus; Model knowledge has the same for its subjects. Each request of the text (its result, each annotation of it, and each earlier result) has "Technical details": the model requested and the model the provider reported, the stop reason, tokens in and out with the reasoning tokens among them, cache read and write, the response ID, the batch ID of a batch, and the run with its prompt version, followed by the raw model output. "Show full request and response" shows the two as the logs of an export hold them: the request the browser sent where it was kept, or built again from the stored settings where it was not, and the Lab's record of the response (the reply, the model and the stop reason the provider named, the token counts, and the IDs; the Lab does not keep a provider's whole reply). A PDF is named and not shown, and no key is part of either. The standard Lab shows none of this. `components/research/technical.tsx` holds the panel, `requestRecord` and `responseRecord` in `lib/research/export-data.ts` are shared with the export, and `tests/text-details.cjs` covers them.
- Annotations per text (Processing options, 1 to 10): a run can annotate each text several times, each time as a request of its own, to see how steady the model's answers are. The text still has one result in the run: the value most annotations gave for a category, a yes / no, or an untyped field (a tied vote reads "a | b"), the median for an ordinal scale, and the mean for a number. An explanation is never a mix: it is the one written by the annotation whose answers are closest to the combined ones. Plain-text replies that are JSON are combined value by value (a score by the median of its numbers, any other value by majority). Every annotation is kept with its own reply, tokens, and times; the results table marks an answer that not all annotations gave with the share that did, and a text with fewer usable annotations than planned says so. After a failed or paused run, "Remaining" makes only the missing annotations, in the same run, while the settings are unchanged. In a batch, each file is sent once and requested as many times as it has annotations to make. Runs & agreement can compare single annotations of a run with each other (a retest). In the exports, the table of requests has a `replicate` column, the results per text have a `<field>_replicate_agreement` column after each combined answer, and the number is in `metadata.json`, the run overview, the README, the draft methods paragraph, and the Python script. The number is part of a run's settings and is stored with the study only when it is more than one; the standard Lab always makes one annotation per text. Model knowledge still makes one annotation per subject. `lib/research/repeats.ts` holds the rules, and `tests/annotation-repeats.cjs` and `tests/research-mode.cjs` cover them.
- Texts: besides one file per text, a whole corpus can be loaded from a table (CSV, TSV, XLSX, JSON, or JSON Lines) with one row per text, or pasted in. Each text is stored as a plain-text document named after its ID, and the table's other columns become labels or metadata.
- Labels and metadata: a CSV or Excel file is matched to the texts by file name. Each column is either human labels or metadata; both can be used to filter, compare, and stratify a sample. A sheet replaces the values of the texts it lists (a blank cell leaves no value); texts it does not list keep theirs unless the dialog is asked to remove them. One row per text: several rows for a text are merged when they agree and refused when they differ. A results file exported from the Lab is refused, since its values are the model's answers. A column named after an answer field, or with a word such as coder, rater, or gold, is first guessed to hold human labels.
- Scale of the scores: for plain-text replies that are JSON, a scale set for the study (for example −3 to 3) under Answer fields. It is never sent to the model. Agreement then uses every point of it, and a number off it is left out and reported; a value answered only with 0 and 1, or mostly off the scale, keeps the range of the answers.
- Placeholders in the prompt: `{{id}}` stands for a text's name and `{{meta.<column>}}` for its value in a metadata column, as in `{{meta.year}}`; each is filled in for every text before the prompt is sent, and the lines under the prompt box say which are filled in. A column of human labels is never sent to the model, so a placeholder that names one is filled in empty, as is one that names no column. Anything else in double braces, such as `{{text}}`, is sent as written (the text always follows the prompt in a message of its own), and the standard Lab fills in nothing. The answer format is read from the prompt as written. With prompt caching on, the cache mark stands before the first placeholder, since that part is all the texts' prompts share; a prompt that begins with a placeholder has nothing to cache. Each result keeps the values its request was sent with, the recorded request holds a mark for each placeholder (`<<INSERT:meta.year>>`), the logs give every request as it was sent, and the exported script fills the placeholders from the corpus table. `lib/prompt-inserts.ts` holds the rules and `tests/prompt-inserts.cjs` covers them.
- System prompt (under the prompt, optional): a system prompt of your own, sent unchanged with every request in the provider's place for one (OpenAI `instructions`, Claude `system`, Gemini `systemInstruction`, an OpenRouter system message). The annotation prompt, with the Lab's answer instructions, then opens the message with each text. Left empty, requests are as before: the annotation prompt is the system prompt. It is kept with the study, its runs (a changed system prompt starts a new run and prompt version), saved prompts, and backups; it is counted in the cost estimate, shown in Preview request and a run's Settings, and written into the exports (`system_prompt.txt`, the Settings sheet, `metadata.json`).
- Samples: "Draw a sample" marks a random sample, optionally stratified, with a recorded seed so the draw can be repeated.
- Deleting texts (the More menu above the results table): "Delete N selected texts…" and "Delete all texts…". A text that a run sent a request for leaves the Workspace and is never annotated again, but it stays with that run: in Runs & agreement (the runs table, the comparisons, the comparison report) and in the Export tab's files, in its place among the study's texts, and the corpus table marks it with the date in `removed_from_study`. Two columns of human labels are compared on the texts still in the study. A text no run used is deleted outright. The same text added again (the same name and the same bytes, or the same name and text from a table or pasted text) gets its record back, results and all; a different text from a table or pasted text under its name gets a new name, as one under a name in the Workspace does. A deleted text goes for good when no run uses it any more (its runs were deleted), and with "Clear results" or "Clear workspace." The rules are in `lib/research/removed.ts`.
- The runs table (Runs & agreement): each run has a label of its own (up to 80 characters, kept with the study and in the run overview of the exports), its scope (what the button that started it covered, such as "All texts (6)", "Remaining of the selected texts (3)", or "One text: speech-4.txt"; a run continued later lists each start), its status (running, submitted, completed, or failed), its requests (OK / failed), its tokens in and out, and its cache read and write. "Settings" shows what the run was started with: the provider and model, the reasoning effort, the prompt and its version, the processing options, the answer fields, the scope, the retries, and the request body it shared, as it was kept when the run was made, with no key. "Retry failed" sends the requests of the run that have no usable answer (failed texts and missing annotations) again, with the run's own settings even when the Workspace now holds others, and the answers join the same run; the failed attempts stay in the exports. It sends immediate requests, also for a run made as a batch (at full price, and the confirmation says so). Model knowledge runs have no label, scope, or "Retry failed": failed subjects are sent again from Model knowledge. `lib/research/runs.ts` holds the rules, `components/research/runs-panel.tsx` the table and the Settings window, and `tests/runs-table.cjs` and `tests/research-mode.cjs` cover them.
- Runs & agreement compares a run with human labels or with another run: percent agreement, Cohen's κ, weighted κ, Krippendorff's α, Gwet's AC1 and AC2, with 95% intervals, a confusion matrix, and the list of disagreements. Where a run's field declares its scale or categories, the statistics use them (so Gwet's coefficients and the weights rest on the whole scale, and a label that is not on it is left out and reported); otherwise the scale is read from the run's answers (from both runs' answers when two runs are compared, so the figures do not depend on which comes first), and the page says which. "At a glance" above the statistics says how many texts got the same answer, how many differ by 1 and by 2 or more points (a bar), which side gives the higher values, how many land on opposite sides of the middle of the scale, and, for categories, the three commonest mix-ups.
- Comparison report (Runs & agreement, when two runs are compared): "Download comparison report (Excel)" makes one workbook for every answer field the two runs can both be compared on. Summary: the figures with 95% intervals (exact agreement, within the tolerance, a difference of 2 or more points, opposite direction, weighted κ, Krippendorff's α, Cohen's κ, Gwet's AC1 and AC2, the mean difference, and Spearman's ρ), with a second row on the texts where at least one run gave a score other than 0 when both runs gave some texts 0. Draft text: a sentence per field for a paper. Review: every compared pair with both explanations, ordered for expert review (opposite directions first, then the largest differences), with a fixed `random` column for a draw that can be repeated and empty `judgment` and `note` columns. "Break down by" a column with 2 to 30 values adds the same figures per value (exploratory). Runs: the two runs' settings side by side. A table of the values per field (up to 15 values), and Notes on how to read it all. The pairing and the statistics are those of the page; the intervals are computed in a background worker. `lib/research/comparison-report.ts` builds it, and `tests/comparison-report.cjs` covers it.
- Export: one run is chosen as the run to report. The Excel workbook holds that run (a row per text, a row per request, agreement, settings, and an overview of all runs). The research repository (.zip) is the whole study for the researcher's own archive: the corpus, every run with its record, prompt, answer fields, results, and request and response logs, all results in one table, agreement, the samples drawn, and a study backup. The supplementary repository (.zip) is what a journal or a deposit needs for the chosen run: `metadata.json`, the prompt as written and as sent, the answer fields and schema, results per text (`results.csv`) and per request (`results_by_replicate.csv`), agreement, a README with a draft methods paragraph, and a Python script that sends the requests again; the texts, the model's explanations, and the logs are each optional. Agreement is computed without anyone choosing pairs: a column added as human labels is compared with the answer field it is named after (`tone_human`, `human_tone`), or with the run's only field, and two such columns of one field with each other; a column left out is listed with the reason. The logs are made from the kept requests with each document put back, so a request line is what was sent, and a response line holds what the Lab kept of the reply, not the provider's whole response. The Python script uses only the standard library and sends the kept request body unchanged. Every file is made in the browser, and none holds an API key. `lib/research/export-*.ts` hold the files and `tests/research-export.cjs` covers them, including a run of the script against a local stand-in for each provider (skipped where Python is not installed).

The code is in `lib/research/` (logic and statistics, covered by `tests/research-lib.cjs`) and `components/research/` (interface, loaded only when research mode is on). `tests/research-mode.cjs` checks the switch, the keys, and that the standard Lab shows nothing of research mode. Code that both modes need, such as the model lists and provider calls, is shared, not copied.

## Working on it

Requires Node.js 22 or later.

```sh
npm ci          # install
npm run dev     # local preview at http://localhost:5173
npm run build   # static build in dist/client
npm test        # all tests (provider traffic is mocked; no real keys)
```

Every push to `main` builds, tests, and publishes the site (`.github/workflows/pages.yml`). Propose changes as pull requests so they can be reviewed before going live.

The embed snippet for the ASCA page (AU's TYPO3 content element) is in `docs/au-embed.html`. Editorial conventions are in `AGENTS.md`.
